# ADR 0006: هستهٔ مشترک و مرزهای پلتفرم

## وضعیت

پذیرفته‌شده؛ مرحلهٔ آماده‌سازی Android در نسخهٔ 0.56.14. تصمیم ماژول‌ها جایگزین ساختار تک‌ماژولی پیشنهادی در ADR 0001 است. Windows و iOS هنوز محصول قابل انتشار نیستند.

## زمینه

فرمول‌ها و مدل‌های کسب‌وکار قابل اشتراک بودند، اما همراه UI و آداپتورهای Android در `app` کامپایل می‌شدند. وابستگی به زمان، UUID، قالب‌بندی Java و Calendar مانع کامپایل Kotlin مشترک بود. ساخت repository در ViewModelها و صفحهٔ اصلی، و ثبت موجودی اولیه در composable، آزمون و مهاجرت را دشوار می‌کرد.

## تصمیم

- `app` میزبان Android، Compose، Room، WorkManager، HTTP/JSON، فایل/PDF، انتخاب لوگو و احراز هویت زیستی می‌ماند.
- `core` یک ماژول Kotlin Multiplatform با هدف‌های Android و JVM است. `commonMain` شامل مدل‌ها، سیاست‌های محاسبه/گزارش/فاکتور، قراردادهای repository، تراکنش و تکمیل راه‌اندازی است.
- نام package، فیلدهای مدل، شناسه‌ها، فرمول‌ها و سیاست گردکردن فعلی حفظ می‌شوند. انتقال فایل، مهاجرت schema یا داده نیست.
- آداپتورهای زمان، UUID، قالب‌بندی و تقویم با `expect/actual` در `platform` تعریف می‌شوند. `jvmSharedMain` پیاده‌سازی Java فعلی را بین Android و JVM به اشتراک می‌گذارد؛ افزودن iOS نیازمند actual بومی و تست سازگاری جداگانه است.
- `GoldexApplication → AndroidAppContainer` نقطهٔ ساخت وابستگی‌هاست. Factory صریح، ViewModelها را با constructor injection می‌سازد. Context در آداپتور Android می‌ماند؛ ViewModelهای اصلی، لایسنس و همگام‌سازی دیگر AndroidViewModel نیستند. لایهٔ همگام‌سازی همچنان Android است و در این مرحله قرارداد عمومی جدید برای sync اختراع نمی‌شود.
- قراردادهای خواندن cache، انتخاب اولیهٔ منبع و وضعیت شبکه جدا هستند. بارگذاری cache نباید درخواست شبکه بسازد. ViewModel اصلی dispatcher کاری قابل تزریق دارد.
- `OpeningInventoryPolicy` طرح موجودی اولیه را می‌سازد. `CompleteOnboardingUseCase` تنظیمات کسب‌وکار، انبار، پورتفولیو و marker فعلی `onboarding-complete` را در همان Unit of Work ثبت می‌کند. UI فقط رویداد می‌فرستد و پس از commit داده‌ها را بازخوانی می‌کند.
- اجرای مجدد ویزارد، با marker موجود یا پرچم تکمیل نسخه‌های قدیمی، موجودی را دوباره ثبت نمی‌کند؛ تنظیمات قابل ویرایش باقی می‌مانند. دادهٔ بازیابی‌شده از cloud بر ورودی‌های افتتاحیه مقدم است و هیچ تراکنش مالی جدیدی انجام نمی‌شود. پرچم محلی تکمیل پس از موفقیت ثبت می‌شود.
- وابستگی‌های تولید جدید صرفاً پلاگین موجود Kotlin Multiplatform و Android library هستند. Hilt/Koin یا موتور UI جدید افزوده نمی‌شود.

## اصول و الگوها

- **SoC / SRP:** نمایش، state، سیاست موجودی اولیه و ماندگاری صاحبان مستقل دارند.
- **DIP / Ports & Adapters:** use case و state اصلی از قراردادها استفاده می‌کنند؛ Android پیاده‌سازی را انتخاب می‌کند.
- **ISP:** خواندن cache و مشاهدهٔ اتصال از عملیات بازار جداست؛ مصرف‌کننده دسترسی به Context یا دیتابیس نمی‌گیرد.
- **OCP:** افزودن آداپتور جدید نیازمند بازنویسی فرمول‌ها نیست.
- **LSP:** قرارداد جایگزینی با تست‌های رفتار، دادهٔ قدیمی و rollback بررسی می‌شود؛ وجود interface به‌تنهایی تضمین آن نیست.
- **Repository، Factory و Unit of Work:** الگوهای موجود حفظ و در composition root به هم متصل می‌شوند.

## پیامدها و محدودیت‌ها

- Android همان هسته‌ای را مصرف می‌کند که روی JVM آزموده می‌شود؛ نسخهٔ JVM یا runtime دسکتاپ در APK قرار نمی‌گیرد.
- افزایش اندازهٔ APK از روی artifact امضاشدهٔ CI سنجیده می‌شود؛ تغییر Gradle module تضمین ثابت ماندن اندازهٔ باینری نیست.
- فرمول‌ها و برخی مدل‌های قدیمی هنوز Double دارند. تبدیل پول به نوع دقیق، تصمیم و تست سازگاری مستقلی می‌خواهد.
- APIهای همگام repository، query روی ترد اصلی، parsing اختصاصی بازار، JSON در state ابری، PDF و سرویس‌های Android هنوز مرحلهٔ مهاجرت بعدی دارند.
- MainViewModel همچنان پوسته، بازار و بخشی از state محاسبات را هماهنگ می‌کند؛ هر قابلیت بعدی باید owner ویژگی را استخراج کند و state را دو بار مالک نشود.
- UI مشترک، بسته‌بندی Windows/macOS، actualهای iOS و signing آن‌ها در این تغییر اجرا نمی‌شوند. ابتدا Android باید روی دستگاه پایدار شود.

## بررسی و شرایط بازنگری

- اجرای محلی `compileDebugKotlin` و `testDebugUnitTest` الزامی است؛ assemble و signing فقط در CI انجام می‌شوند.
- `:core:verifyCoreBoundaries` metadata مشترک را کامپایل و importهای Java/Android/AndroidX/JSON را در commonMain رد می‌کند.
- تست‌های دامنهٔ موجود روی Android و JVM اجرا می‌شوند. تست‌های جدید سازگاری نمایش فارسی، راه‌اندازی بدون شبکه، ورودی مالی، ثبت تکراری و rollback واقعی Room را بررسی می‌کنند.
- هنگام آغاز Windows، قرارداد فایل/PDF، ذخیره‌سازی و شبکه، چرخهٔ عمر، ورودی صفحه‌کلید/ماوس و RTL روی دسکتاپ بازنگری شوند.
- هنگام آغاز iOS، قالب‌بندی، timezone، UUID، threading و نتایج مالی باید در actualهای بومی همان خروجی‌های تأییدشده را بدهند؛ تغییر toolchain یک تصمیم جداگانه است.
